Calling something “Databricks for agents” suggests a platform where developers can store agent data, run computations over it, evaluate behavior, and build better models. Databricks already supports that workflow, alongside the infrastructure that runs the agents themselves.

That is the interesting part of the exchange between Harrison Chase and Ali Ghodsi. Chase used the Databricks analogy to describe a broader ambition for agent observability. Ghodsi’s reply was that Databricks itself occupies that position. The way to examine that claim is to follow the actual developer workflow: which services execute an agent, where its data goes, what you can compute over that data, and how a new model gets back into production.

By the end of October 2026, that workflow spans Agent Bricks, Unity Catalog, Genie, AI Search, MLflow, AI Runtime, and Model Serving. AIR’s NVIDIA integration and custom vLLM serving are particularly significant: the platform can support teams that want to adapt and operate open models, as well as teams consuming hosted model APIs.

This article walks through those connections. A retail support agent provides a running example, using the open τ-bench environment and inclusionAI’s related training data as reference material. The subject is the Databricks platform: what each capability contributes and what passes from one capability to the next.

I’m an AI Solutions Architect at Databricks. This is my technical reading of the documented platform as of 31 October 2026. The interactive diagrams explain its components; they do not connect to a live workspace.

The platform argument

Start with the connections.

Databricks brought data engineering, analytical queries, machine learning, and governance into a shared environment. Agent development creates work for each of those systems. Conversations and tool calls become datasets. Developers query those datasets, add assessments, run evaluations, and sometimes use the reviewed examples to adapt a model.

There is also an online application to operate: it needs identity, session state, tools, memory, model access, and compute. Databricks has added those services around the data and ML platform. Context and tools

Give the agent access to the data platform.

An agent working on a support request may need three different kinds of information: passages from a manual, facts from an order database, and something retained from a previous conversation. Treating all three as a vector lookup makes the application harder to reason about. Databricks provides distinct access paths.

AI Search, formerly Vector Search, builds retrieval indexes over source tables and can synchronize them as the source changes. Hybrid search combines keyword matching with semantic similarity; filters and reranking provide further control. That is useful for support documents containing exact product codes as well as natural-language descriptions. [3]

Genie One MCP gives the outer agent an analytical tool. It can ask a data question and receive an answer backed by SQL results and cited sources. Genie Ontology supplies governed definitions and relationships, while Unity Catalog permissions constrain access. The outer agent can delegate the analytical subtask instead of discovering a warehouse schema from scratch. [4]

Agent memory is a managed, Lakebase-backed store for durable information across conversations. Sessions hold the conversation in progress. Memory entries can be written by the application or derived through a memory pipeline. The application must choose the right access boundary: actor identifiers organize entries, while permissions are enforced at the store level. This feature is Beta at the article’s date. [5]

MCP services and application tools extend the agent beyond retrieval. A custom tool can look up an order or create a return; Databricks-managed tools expose platform capabilities. The harness still owns tool selection, and the application tool owns the transaction it performs. Databricks supplies the surrounding identity and access mechanisms. [6]

In a retail implementation, I would use direct typed tools for individual order operations, AI Search for manuals, and Genie for aggregate questions about support traffic. That keeps each interface suited to its job. It also leaves a clearer execution record than forcing every request through the same generic retrieval function.

Unity Catalog and Unity Gateway

Apply controls to models and tools as well as data.

An agent introduces new access questions: which model can it call, which MCP tools can it invoke, which identity does a request use, and how is consumption tracked? Unity Gateway extends the platform’s governance model to supported AI services. Model services, MCP services, functions, and connections can be governed resources rather than configuration scattered across individual agents. [17]

Service policies add request and response controls. Teams can configure access, rate limits, guardrails, and usage tracking for the supported service paths. This lets a platform team manage model and tool access while application developers keep their framework and harness choices.

The application identity remains explicit. Agent Runtime uses the app’s service principal; configured user-authorized tools use the requesting user’s permissions. Endpoint-specific feature support still matters, especially for custom model serving. [7] [19]

Agent infrastructure

Run your harness on Agent Runtime.

Agent Bricks now describes the developer platform for bringing an agent built with your choice of framework or harness. Genie Agents provides a separate route for creating agents without writing the orchestration yourself; custom agents can call Genie Agents as tools. This distinction matters when reading older material that uses “Agent Bricks” more narrowly. [1]

For a custom application, Agent Runtime hosts the agent server on Databricks Apps. A deployment has an authenticated endpoint, an app service principal, and configured MLflow tracing. The documented CLI provisions or reuses declared memory and session resources; with DurableAgentServer it also provisions the Runtime Store used for recovery. [7]

Agent Bricks CLI / documented deployment command
agentbricks --profile <profile> deploy my-agent

DurableAgentServer handles the request lifecycle, including streaming and background runs with persistent state. Databricks Sandbox gives an agent a separate environment for executing generated code. Those are different responsibilities from loading a model on a GPU. Sandbox is Beta and has its own quotas and runtime limits. [8] [9]

The terminology is worth making explicit. Agent Runtime runs the application. AI Runtime supplies GPU compute for model development and other GPU workloads. Model Serving hosts inference. A support agent can run on Agent Runtime while its open model runs on a separate GPU endpoint, with AIR used only when the team trains or experiments with that model.

Agent data and computation

A trace belongs in the data platform, too.

This is where the original Databricks analogy becomes especially concrete. Agent runs produce substantial datasets: prompts, responses, retrieved passages, tool arguments, execution paths, and reviewer assessments. An execution viewer lets you inspect a run. A data platform lets you work across the collection.

Databricks documents OpenTelemetry ingestion into Unity Catalog tables, with MLflow providing the agent-facing tracing and quality workflow. Once executions are available as governed data, developers can query them with SQL, join them to application metadata, and use pipelines to produce analysis tables. The trace need not originate from an agent hosted on Databricks. [2]

Suppose a reviewer identifies repeated tool-argument errors. The next task is to find similar runs, group them by model and harness version, and build a reviewed collection. SQL handles the grouping and joins. AI Functions can help annotate the text. MLflow retains the detailed execution and assessment context.

These queries illustrate the workflow and have not been executed here. The AI classification tab creates candidate annotations; human review and evaluation determine whether they are useful.

The AI Functions layer makes language-model operations available within SQL and data workflows. You can classify an execution summary, extract fields, or call a supported endpoint through ai_query, then continue processing the resulting columns. This brings language-model computation into the same workflow as filtering, aggregation, and joins. Inference and query compute have their own costs, so these jobs should be measured like other production pipelines. [10] [11]

That is a substantial reason to use the word “Databricks” in this category. The team is working with an agent’s accumulated data using the analytical and engineering environment it already uses for other data. The execution viewer is one interface to that data; it does not define everything the team can do with it.

MLflow

Move from an observed run to a tested change.

MLflow connects tracing with feedback, datasets, scorers, evaluation, and production monitoring. A reviewer can assess a failing execution in context. Representative examples can then enter an evaluation dataset, where code-based checks or model-based judges test subsequent versions. That gives a prompt edit, a tool fix, or a model change a repeatable comparison. [12]

For the retail example, a tool-argument check might verify that the requested item IDs match the order items. A response check might verify that the final answer reflects the tool result. These are different questions, so I would retain separate scores rather than compressing everything into a single helpfulness judgment.

MLFLOW TRACEExecutionModel and tool spans
EXPERT REVIEWAssessmentWhat should change
DATASET + SCORERRegression testRepeatable comparison

Evaluation matters to the platform story because it connects the application developer’s work to the model developer’s work. Both can use the same reviewed cases to investigate a problem, while keeping training data separate from held-out evaluation data. Live monitoring can apply scorers to sampled production traffic; that capability is Beta at the time of writing. [13]

Genie Code also appears in the documented MLflow workflow for exploring traces and finding issues. It is useful as a development interface over the execution data. The underlying traces, assessments, and evaluation definitions remain the records against which a proposed change is checked. [12]

AI Runtime and NVIDIA

The platform includes the work of building a model.

A team may begin with a hosted model and later decide to adapt an open model for a recurring task. That adds a different workload: prepare examples, configure training, obtain GPUs, run experiments, save checkpoints, and evaluate the result. AI Runtime puts that work inside Databricks.

AIR became generally available on 21 October 2026. It provides managed GPU infrastructure and supports code, custom containers, and distributed workloads. The integration with the surrounding platform matters as much as the GPU allocation: datasets can remain under Unity Catalog, MLflow records the experiment, and Lakeflow Jobs can orchestrate the work with upstream preparation and downstream evaluation. [14]

The AIR CLI is one documented interface for submitting a configured workload:

AI Runtime CLI / workload configuration required
databricks air run --file workload.yaml --watch

The runtime supports fine-tuning, reinforcement learning, distributed training, and batch inference. Its examples include small single-GPU jobs as well as multi-GPU recipes. You select the hardware and software configuration that fits the workload; training capacity and online serving capacity are distinct resources. [15]

What the NVIDIA integration adds

The October announcement makes this concrete through NVIDIA NeMo, NeMo Automodel, NGC containers, and Nemotron cookbooks. Developers can bring an NVIDIA software environment through Artifact Registry, run it on AIR’s managed GPUs, and track the resulting experiments. Genie Code and NVIDIA-specific Agent Skills can help author and debug the training code. [16]

For someone already working with the NVIDIA ecosystem, that is a recognizable software path: use an appropriate NeMo recipe and container, work with governed training data, inspect the run in MLflow, and move the selected artifact toward deployment. The developer still controls the training objective, data, and configuration.

The open-model story therefore covers more than the ability to call a public model API. It includes changing the model and retaining the relationship between its data, training run, evaluation, and deployed version. That is the machine-learning side of “Databricks for agents.”

Model choice and inference

Use a hosted model, or bring the inference stack.

There are several ways to supply an agent’s model. Foundation Model APIs provide Databricks-hosted models. Unity Gateway provides a governed access path for supported hosted and external endpoints. Custom Model Serving addresses the case where a team has its own checkpoint, adapter, or inference requirements. These choices belong in the architecture rather than being hidden behind the phrase “the LLM.” [17]

The custom LLM documentation now describes a vLLM path: test the server in an AIR notebook, package its command and environment, register the model, and deploy a GPU endpoint. Qwen, Gemma, embedding, and speech examples illustrate the breadth of the inference layer. Support depends on the particular checkpoint, hardware, and runtime. [18]

The packaged environment is useful because serving behavior depends on more than weights. The tokenizer, chat template, tool parser, runtime libraries, and inference flags all affect the endpoint. A release should identify them together. Express deployments provide the environment-packaging mechanism used by this route. [22]

There is also a documented LoRA-serving path: one base model can support several adapters selected per request. That is relevant when several specialized agents share a base model. Model evaluation still determines whether each adapter is useful, and workload testing determines the capacity required. [18]

The current boundary is specific. This custom vLLM route is Public Preview, has cloud and region constraints, and does not offer dynamic autoscaling. The gateway capability matrix also differs for custom endpoints: do not assume they inherit every guardrail or fallback feature of external-model endpoints. These are deployment details to resolve, rather than reasons to omit open-model serving from the platform picture. [19]

With the model deployed, the agent harness calls an inference endpoint and records the selected version in its traces. The next evaluation can compare a hosted reference, the original open model, and an adapted checkpoint against the same tasks. This closes the model-development path back into agent development.

An example that exercises the stack

Use retail tool calling to make the platform visible.

Sierra’s τ-bench family provides simulated users, domain instructions, executable tools, and task evaluation. Retail tasks make the tool interactions easy to inspect: find an order, identify an item, collect the required information, and invoke an operation. The benchmark environment is useful here because it gives the model something concrete to do. [20]

For candidate adaptation data, inclusionAI publishes AReaL-tau2-data. Its card lists 11,395 retail SFT records and 563 retail RL records, with source identifiers and environment data. The SFT count refers to assistant-turn records with context, not independent conversations. Before using it, a team would pin compatible revisions, group related dialogues, and check overlap with held-out evaluation. [21]

Why the name fits

The case for Databricks is the full workflow.

Databricks can supply an agent’s context and tools, host its application, provide its model access, retain its state, and capture its executions. The same platform can then process that execution data, evaluate changes, run GPU training, and host an adapted open model.

The connections are practical: source tables feed retrieval; traces feed analytical queries and evaluation datasets; reviewed data feeds AIR; a registered model and packaged environment feed serving; the resulting endpoint feeds the next agent execution. Unity Catalog, MLflow, and the compute services give those steps a shared place to operate.

That is why Databricks is Databricks for agents. It carries the data-and-AI development workflow into agent systems, including the parts that happen before a request and after a response.
