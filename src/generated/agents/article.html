HCHarrison Chase @hwchase17 · 30 Oct

AGAli Ghodsi @alighodsi · 31 Oct

bro, databricks very much is databricks for agents

I work at Databricks, so you already know which side of this I’m on. Still, I think Chase made the more interesting point, and I want to take it seriously before I make my case. He is saying that the hard part of running agents is not watching them. The hard part is what you do with everything they leave behind.

A monitoring tool answers “is it up, and how slow is it?” The questions a team asks after its agent ships are different. Why did it exchange the wrong item? How often does that happen? Did it start with Tuesday’s prompt change? Would a small open model trained on our own conversations do better, and where would we serve it? Each of those is a question about data, and most of them need that data joined to other tables, labeled, and turned into a test set or a training set. Databricks was built for that kind of work long before anyone called a loop an agent.

This post follows one bad tool call through Databricks as it stood on 31 October 2026: a retail support agent that exchanges the wrong item, from the first request to a retrained model. You can drag that trace around the loop, and query 480 synthetic traces to see why a table beats a trace viewer for this kind of question.

Watching is the easy part

A trace from a web service tells you that a database call took 40 milliseconds. A trace from an agent holds much more: the prompt, the passages it retrieved, the arguments the model picked for a tool, and the text it wrote back. The failures that matter are rarely exceptions. The tool call succeeds; it just does the wrong thing. You find those failures by reading traces, labeling them, and counting. You fix them by changing a prompt, a tool, or the model, and then you check that the fix held.

The best public example I know comes from Zepto, the Indian quick-commerce company. Their support system handles more than a hundred thousand tickets a day, and AI agents fully manage more than 80% of them with human oversight. Over six months their evaluation dataset grew from 500 examples to 2,000 and then to 5,247. Over the same period, the gap between accuracy in development and accuracy in production fell from 8 points to 0.4. [2]

Those extra 4,700 examples did not come from a dashboard. Zepto routed production failures back into the dataset, scored every candidate version against it, and rejected any version that did not match or beat the one in production. That is a data pipeline with an agent at one end. It is also the shape of the whole argument for Databricks: the agent produces data, the data becomes tests and training examples, and the tests and examples change the agent.

The loop, one trace at a time

Here is that loop for the support agent, as six stops. Drag the dark dot around the ring, or click a stop. At each stop the same piece of evidence changes shape, and the panel shows which part of Databricks handles it.

Each stop is a separate product, and you can use any of them alone. A team running agents on its own servers can still send traces to Unity Catalog. A team that never trains a model can still use the evaluation tools. The reason to keep them together is what moves between the stops. The trace, the labeled row, the test case, the checkpoint, and the endpoint all sit in one catalog, under one set of permissions, with lineage between them. Nobody exports a CSV of “bad traces” to another system and loses track of where it came from.

Running the agent

Agent Bricks is the name Databricks now uses for its agent developer platform. The docs put it plainly: “You bring an agent built with any framework or harness and choose any model.” [4] Databricks said in June that more than 100,000 agents had been built on it since launch. [3]

A custom agent deploys to Agent Runtime, which runs it as a Databricks App. The app’s service principal is the agent’s identity. One command deploys it, turns on MLflow tracing, and creates the memory and session stores the agent declares. [5] Run state lives in a Runtime Store, so a customer who asks for an exchange and closes the tab doesn’t lose the exchange when a worker restarts. [6]

agentbricks --profile <profile> deploy support-agent

The context comes from pieces built for each kind of question. AI Search, the new name for Vector Search, retrieves policy passages with hybrid keyword and vector search. [7] Genie One MCP answers questions about the business, with links back to the sources it used. [8] Agent memory, stored in Lakebase, remembers what the customer said last time. [9] MCP servers carry out actions on the order. [10] Unity Gateway sits in front of the model and MCP calls, so one team sets the limits and policies, and the usage lands in system tables. [12]

One detail changes how I would build this agent. Memory permissions apply to a whole store, not to single entries. If two customers must never see each other’s memories, they need separate stores, not separate actor IDs in one store. [9]

None of this requires Chase’s company to lose. A LangGraph agent runs on Agent Runtime like any other harness. An agent running anywhere can send OpenTelemetry traces into Unity Catalog, whatever else it sends them to. Databricks cares about the data your agent produces, whichever framework produced it.

A trace is a row in a table

This is the part of the exchange I agree with most. Since May, any OpenTelemetry client can write traces straight into Unity Catalog tables, with no limit on storage. [13] Once traces are rows, the useful questions become queries.

Below are 480 synthetic traces from the support agent, with one problem planted in them. Start with the single trace a viewer would show you, then switch to all traces and try each grouping.

Grouped by tool, exchange_items fails 22% of the time. That is a real lead, but it doesn’t tell you what to fix. Grouped by harness version, v13 fails more often than v12. Cross the two and the cause appears: v13 breaks exchanges on 25 of 55 traces, while v12 breaks one exchange out of 63. Grouped by model, both models fail at the same 7.1%, so moving to a bigger model would not have helped. The planted cause is a change to the item-selection prompt in v13.

In a real workspace I would go one step further and join the failing traces to the orders table, to see whether the failures cluster on orders that contain two variants of the same product, such as a blue shirt and a black one. That join is easy when traces and orders sit in the same catalog. It is hard when the traces live with an observability vendor and the orders live in your lakehouse.

The language model can join the query too. ai_classify labels each failing trace with a reason, and Genie Code answers questions about traces in plain English if you would rather not write SQL. [14] [15]

Failures become tests

The button in the explorer that adds traces to the evaluation dataset is the most important step in the loop. In MLflow, those traces become an evaluation dataset, and scorers check every new version against it. A scorer is either an LLM judge or a plain code check. [15]

For the exchange bug I would write two scorers and keep them separate. The first is code: did the item IDs passed to exchange_items match the item the customer described? The second is a judge: does the reply to the customer match what the tool did? A single “helpfulness” score would blend the two failures, and you would lose the signal that tells you which one a change fixed.

@scorer
def right_items(trace, expectations):
    call = trace.search_spans(name="exchange_items")[0]
    return call.inputs["item_ids"] == expectations["item_ids"]

mlflow.genai.evaluate(
    data=exchange_failures,
    predict_fn=support_agent,
    scorers=[right_items, reply_matches_tool],
)

Zepto’s write-up describes a regression of this kind. A change dropped intent accuracy on one cancellation flow from about 92.1% to 87.4%. Their evaluation caught it, and the fix brought the flow up to about 94.2%. [2]

The same scorers can also run on a sample of live traffic, which is how Zepto spots new failures within four to six minutes. [2] [16]

Training and serving an open model

Most teams should stop at prompts, tools, and tests. Some shouldn’t. If the agent makes the same decision millions of times a day, or the hosted model is too slow or too expensive for it, a small open model trained on your reviewed traces may do better. An observability tool stops before this point. Databricks doesn’t.

AI Runtime, or AIR, became generally available on 21 October. It brings managed GPUs into Databricks: you bring the code, containers, or Ray workloads, and Databricks finds the capacity. [17] The worked examples include full fine-tuning of Qwen3.5-0.8B on one H100, LoRA on GPT-OSS 120B across eight, and reinforcement learning on Gemma4-2B. [19] The NVIDIA partnership announced the same day brings NeMo, NGC containers, and Nemotron cookbooks into AIR, so a team that already uses NVIDIA’s recipes can keep them. [20]

databricks air run --file workload.yaml --watch

The training data should be your own reviewed traces, kept strictly apart from the ones in your test set. If the two overlap, the evaluation measures memory instead of skill. A public dataset such as inclusionAI’s AReaL-tau2-data, with 11,395 retail tool-use examples, makes a reasonable warm-up. [21] [22]

Then the checkpoint has to go back to the agent. Databricks now documents serving custom LLMs on vLLM, including several LoRA adapters on one base model, which suits a team with several specialized agents. [23] The agent calls the new endpoint, the next trace records which version answered, and the same evaluation dataset compares the hosted model, the base open model, and your adapter on the same cases. That is the loop closing.

This last step is the least mature. The vLLM route is in Public Preview, runs only in US regions on AWS and Azure, and doesn’t autoscale. The docs also say that “AI guardrails and fallbacks are not supported on custom model serving endpoints.” [23] [24] If you need guardrails on an open model today, put them in the agent.

What isn’t finished

A platform post that lists only strengths is an ad, so here is what I would check before relying on each piece, as of today:

  • BetaAgent memory, MLflow production monitoring, full-text keyword search in AI Search, and Databricks Sandbox for running generated code. Sandbox blocks inbound traffic but leaves outbound traffic open, and you can’t change that. [11]
  • Public PreviewCustom LLM serving on vLLM (US regions on AWS and Azure; H100 only in us-west-2), and AIR training on 8×B300. [23] [18]
  • Ends 30 NovemberThe old Beta Genie MCP endpoint at /api/2.0/mcp/genie. Move to system.ai.genie_one_mcp. [8]
  • Gaps I’d like closedDynamic autoscaling and gateway guardrails for custom LLM endpoints, and access control finer than the store for agent memory.

Why the name fits

Chase is right that agent observability looks more like Databricks than like Datadog. The claim I am making is narrower, and you can check it. On Databricks today, the trace from Tuesday’s bad exchange can become a SQL row, a labeled test case, a training example, and finally the endpoint version that answers the next customer. All of that happens in one catalog, under one set of permissions, with lineage from the endpoint back to the trace.

If you run agents and want to try this, start small. Send your traces to Unity Catalog, write one SQL query that groups failures by version, and add the worst 50 to an evaluation dataset. You will learn more from that query than from another week of reading traces one at a time.
