Wherever people build agents, the same question keeps coming up: what will the platform for agents be? The answer usually arrives as an analogy. We need a Databricks for agents, a place that does for agent builders what Databricks did for data teams.

It is a good analogy, and it helps to ask why it works. Databricks became the platform for data because it put the whole job in one place: storing data, transforming it, querying it, training models on it, and controlling who can see what. Agents need that same job done, because most of what an agent produces is data. Every request leaves behind prompts, retrieved passages, tool calls, and replies. Making the agent better means querying that record, labeling it, turning it into tests, and training models on it.

I work at Databricks, so read my answer with that in mind: the platform for agents already exists, and it is Databricks. The place that runs the agent also stores its traces, queries them, tests every new version, fine-tunes an open model on what it learned, and serves that model back to the agent. This post follows one bad tool call through that loop, using a retail support agent that exchanges the wrong item. You can drag the trace around the loop and query 480 synthetic traces along the way.

What an agent leaves behind

A trace from a web service tells you that a database call took 40 milliseconds. A trace from an agent holds much more: the prompt, the passages it retrieved, the arguments the model picked for a tool, and the text it wrote back. The failures that matter are rarely exceptions. The tool call succeeds; it just does the wrong thing. You find those failures by reading traces, labeling them, and counting. You fix them by changing a prompt, a tool, or the model, and then you check that the fix held.

The best public example I know comes from Zepto, the Indian quick-commerce company. Their support system handles more than a hundred thousand tickets a day, and AI agents fully manage more than 80% of them with human oversight. Over six months their evaluation dataset grew from 500 examples to 2,000 and then to 5,247. Over the same period, the gap between accuracy in development and accuracy in production fell from 8 points to 0.4. [1]

Those extra 4,700 examples did not come from a dashboard. Zepto routed production failures back into the dataset, scored every candidate version against it, and rejected any version that did not match or beat the one in production. That is a data pipeline with an agent at one end, and it is the kind of work Databricks was built for.

The loop, one trace at a time

Here is that loop for the support agent, as six stops. Drag the dark dot around the ring, or click a stop. At each stop the same piece of evidence changes shape, and the panel shows which part of Databricks handles it.

Each stop is a separate product, and you can start with any of them. The reason to have them on one platform is what moves between the stops. The trace, the labeled row, the test case, the checkpoint, and the endpoint all sit in one catalog, under one set of permissions, with lineage between them. Nobody exports a CSV of “bad traces” to another system and loses track of where it came from.

Running the agent

Agent Bricks is the Databricks agent developer platform. The docs put it plainly: “You bring an agent built with any framework or harness and choose any model.” [3] More than 100,000 agents have been built on it since launch. [2]

A custom agent deploys to Agent Runtime, which runs it as a Databricks App. The app’s service principal is the agent’s identity. One command deploys it, turns on MLflow tracing, and creates the memory and session stores the agent declares. [4] Run state lives in a Runtime Store, so a customer who asks for an exchange and closes the tab doesn’t lose the exchange when a worker restarts. [5]

agentbricks --profile <profile> deploy support-agent

Each kind of context has its own interface. AI Search retrieves policy passages with hybrid keyword and vector search. [6] Genie One MCP answers questions about the business, with links back to the sources it used. [7] Agent memory, stored in Lakebase, remembers what the customer said last time. [8] MCP servers carry out the actions on the order. [9] Unity Gateway sits in front of the model and MCP calls, so one team sets the limits and policies, and every request lands in system tables you can query. [10]

You don’t have to move your agent to use the rest of the platform. Agent Runtime runs whichever framework you wrote it in. An agent running somewhere else can send its OpenTelemetry traces into Unity Catalog and use everything that follows.

A trace is a row in a table

Any OpenTelemetry client can write traces straight into Unity Catalog tables, with no limit on storage. [11] Once traces are rows, the useful questions become queries.

Below are 480 synthetic traces from the support agent, with one problem planted in them. Start with the single trace a viewer would show you, then switch to all traces and try each grouping.

Grouped by tool, exchange_items fails 22% of the time. That is a real lead, but it doesn’t tell you what to fix. Grouped by harness version, v13 fails more often than v12. Cross the two and the cause appears: v13 breaks exchanges on 25 of 55 traces, while v12 breaks one exchange out of 63. Grouped by model, both models fail at the same 7.1%, so moving to a bigger model would not have helped. The planted cause is a change to the item-selection prompt in v13.

In a real workspace I would go one step further and join the failing traces to the orders table, to see whether the failures cluster on orders that contain two variants of the same product, such as a blue shirt and a black one. That join is one line of SQL when traces and orders sit in the same catalog. It is a project when they live in separate tools.

The language model can join the query too. ai_classify labels each failing trace with a reason, and Genie Code answers questions about traces in plain English if you would rather not write SQL. [12] [13]

Failures become tests

The button in the explorer that adds traces to the evaluation dataset is the most important step in the loop. In MLflow, those traces become an evaluation dataset, and scorers check every new version against it. A scorer is either an LLM judge or a plain code check. [13]

For the exchange bug I would write two scorers and keep them separate. The first is code: did the item IDs passed to exchange_items match the item the customer described? The second is a judge: does the reply to the customer match what the tool did? A single “helpfulness” score would blend the two failures, and you would lose the signal that tells you which one a change fixed.

@scorer
def right_items(trace, expectations):
    call = trace.search_spans(name="exchange_items")[0]
    return call.inputs["item_ids"] == expectations["item_ids"]

mlflow.genai.evaluate(
    data=exchange_failures,
    predict_fn=support_agent,
    scorers=[right_items, reply_matches_tool],
)

Zepto’s write-up describes a regression of this kind. A change dropped intent accuracy on one cancellation flow from about 92.1% to 87.4%. Their evaluation caught it, and the fix brought the flow up to about 94.2%. [1] The same scorers also run on a sample of live traffic, which is how Zepto spots new failures within four to six minutes. [14]

From a trace to a fine-tuned model

Prompt and tool fixes take you a long way. When the agent makes the same decision millions of times a day, a small open model trained on your own traces can answer faster and cost less than a large hosted model. On most stacks, this is where the work leaves the agent tooling. You export the examples, find GPUs somewhere else, track the run in a third system, and then work out how to deploy what you trained. On Databricks the examples never leave the platform.

AI Runtime, or AIR, is serverless GPU compute inside Databricks. It reads training data straight from Unity Catalog tables and volumes, tracks every run in MLflow, and applies the same Unity Catalog permissions to the data, the checkpoints, and the logs. [15] [16] For the support agent, the path from a reviewed trace to a model that serves traffic has five steps, all in one workspace:

  1. Turn reviewed traces into training data.One query selects the reviewed exchanges and leaves out every trace in the evaluation set, so the model is never tested on what it trained on.CREATE TABLE support.train.exchanges AS SELECT prompt, corrected_tool_call FROM support.reviewed_traces WHERE trace_id NOT IN (SELECT trace_id FROM support.eval.exchanges);
  2. Fine-tune on AI Runtime.Point the workload at the table and pick the GPUs. The worked examples include full fine-tuning of Qwen3.5-0.8B on one H100, LoRA on GPT-OSS 120B across eight, and reinforcement learning on Gemma4-2B. [17]databricks air run --file workload.yaml --watch
  3. Compare runs in MLflow.Every run logs its data, metrics, and checkpoints, so the adapter you pick links back to the exact traces it learned from.
  4. Register and serve.Register the model in Unity Catalog and serve it on vLLM. One endpoint can serve several LoRA adapters on one base model, one for each specialized agent. [21]mlflow.register_model("runs:/<run_id>/model", "support.models.exchange_8b")
  5. Evaluate it like any other version.The same scorers that caught the bug now compare the hosted model, the base open model, and your adapter on the same cases. The winner goes into the agent, and its traces start the loop again.

Teams that already work with NVIDIA’s tools can keep them. AIR runs NVIDIA NeMo, NGC containers, and the Nemotron cookbooks, and Genie Code can help write and adapt the training script. [18] On AIR, Superhuman cut a training run from roughly seven days to 48 hours, and FactSet went from days to hours to set up, train, and deploy a model. [15]

Your own reviewed traces are the training data that matters most. For a public warm-up on retail tool use, inclusionAI’s AReaL-tau2-data has 11,395 retail examples built on Sierra’s τ²-bench environment. [19] [20]

The platform for agents

“What will the platform for agents be?” has an answer you can check. On Databricks today, the trace from Tuesday’s bad exchange becomes a SQL row, a labeled test case, a training example, a fine-tuned model, and finally the endpoint version that answers the next customer. Every step runs under the same permissions in one catalog, with lineage from the endpoint back to the trace that started it.

That is what Databricks did for data, and it is what we are doing for agents: taking work that used to need five systems and a lot of glue code, and making it one loop. If you build agents, start small. Send your traces to Unity Catalog, write one query that groups failures by version, and add the worst 50 to an evaluation dataset. When the same failure keeps coming back, train on it.
